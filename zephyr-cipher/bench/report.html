Wired throughput is CPU/PHY-bound at ~3.1 MB/s and rock-steady across a full 100 MB transfer. WiFi tuning (below) lifts the ESP32 8.5×; the measured Espressif ceiling for ESP32-Zephyr WiFi is ~4 Mbps TCP / ~10 Mbps UDP.

04 WiFi: the memory ↔ speed curve

Networking speed trades against RAM. The iface library exposes this as one switch (CK_IFACE_NET_{THROUGHPUT,BALANCED,FOOTPRINT}) driving TCP window, buffer sizes and ESP32 IRAM. The two chokepoints were NET_BUF_DATA_SIZE=128 (a 1500-byte packet shredded across ~12 buffers) and a zero TCP window (no in-flight pipelining).

The tradeoff, made concrete: the original ESP32 has ~320 KB DRAM and WiFi claims ~50. Full-MTU buffers + a 50 KB window on top of cipher's own packet heaps overflow by ~15 KB — so the ESP32 runs BALANCED, its sweet spot. More speed genuinely needs more silicon.

⚠ Reliability caveat

The ESP32 associates and reports link-up but then drops client traffic under sustained load — reproduced with a raw TCP sink (zero cipher), so it is the link, not the protocol. Prime suspect: the AP left in setup mode (SETUP-xxxx SSID). A properly-configured 2.4 GHz AP is the next dependency for sustained WiFi runs.

05 What the stack proved

Protocol

  • RPC round-trip 0.34 ms wired, 1000/1000 correct
  • Streams reassembled + FNV-1a verified to 100 MB
  • Double-sided + concurrent bidirectional
  • Buffer-less generated send — a 16 KB-RAM node sources 100 MB

Architecture

  • Transport-agnostic: identical 3-line app on eth + WiFi
  • Connectivity owned by conn_mgr — coexists with other net apps
  • Multi-instance: two daemons, one image, verified
  • Parity C ↔ Go, wire-compatible, golden vectors

Hardware

  • STM32 H743 (eth) — solid
  • ESP32 ×2 (WiFi) — tuned, AP-limited
  • Slot-4 PHY dead (bare-metal MDIO confirmed)
  • WiFi creds provisioned once to NVS
