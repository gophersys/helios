# _build/upstreams.txt — where the next value of every pin comes from.
#
# Every pin of the value homes carries exactly 1 row here, and every row names a
# pin that exists. `_ctl/tests/upstream-coverage.test.sh` holds both directions,
# reading the pins out of the HOMES and never out of this table: a rule that
# read the listing would go on reporting coverage after the pin it covers was
# renamed.
#
# The homes are `PIN_VALUE_HOMES` in `_ctl/lib.sh` — read that list, never a
# count of it here. base/Dockerfile was one of them until its ARGs went
# value-less; every pin it used to declare is a versions.env row now, and the
# row a pin takes here did not move with it, because a row is keyed by the PIN
# NAME and no name changed.
#
# The grammar is the grammar of its neighbour _build/download-exemptions.txt —
# 1 table shape in _build/, not 2 — 4 fields, none empty:
#
#   <pin>|<datasource>|<coordinate>|<policy or reason>
#
# The 12 datasources. 11 of them resolve a version from an upstream and are
# driven, 1 stub pin each, by `_ctl/tests/resolve-upstream.test.sh`:
#
#   github-release    the newest release github marks latest, of <owner>/<repo>
#   pypi              info.version of <package> on the index
#   npm               dist-tags.latest of <package> on the registry
#   apt               the newest published binary of <package>@<ubuntu series>
#   go-dl             the newest stable release of the go download index
#   node-dist         the newest LTS release of the node distribution index
#   oci-index         the INDEX digest <repository>:<tag> holds now
#   k8s-dl            the <channel>.txt release channel of dl.k8s.io
#   tailscale-pkgs    the <channel> package index of pkgs.tailscale.com
#   flutter-releases  the <channel> channel of the flutter linux release index
#   eden-manifest     the value gophersys/eden pins in <repo>:<path>
#
# The 12th is `no-autobump`, which resolves nothing. Its 4th field is the REASON,
# and it has to be a sentence: `n/a`, `todo` and `-` all pass a non-empty test,
# and each one is a pin nobody decided about wearing the label of a pin somebody
# did. 16 pins take it today.
#
# A reason has to be TRUE, and nothing in the pull request gate can check that.
# 3 of these rows were corrected after their reasons were measured against the
# real upstreams: the android index this file said did not exist does, and 2
# github-release coordinates could never have resolved at all. A reason nobody
# measures is the same defect as a pin nobody watches, 1 level up.
#
# The download URL is deliberately NOT here. The resolver reads it out of the
# file that performs the download, because the digest must be of the bytes the
# BUILD fetches; a second URL home lets a correct digest be computed of the
# wrong asset. The `# upstream-published: <url>` comment beside each digest row
# already names the checksum file, and it gets no second home either.
#
# A github-release row rests on the release github marks `latest` being the
# release of the tool this pin names. For a repository that publishes several
# products under one release stream that is not true, and the weekly run then
# FAILS naming the pin when the asset URL 404s. The answer is a corrected row or
# a no-autobump row, decided by a human — never a silent skip.

# -------- no-autobump: the pins that are not a version --------
# Each of these selects a MAJOR line or a channel inside a name, so the value an
# upstream would report is not the value the pin spells: python3.13 is a
# different package, openjdk-22-jdk-headless is a different package, and
# resolving stable to a number would freeze the channel this pin exists to
# follow.
PYTHON_PACKAGE|no-autobump|python3.12|the pin is an apt PACKAGE NAME carrying the major line, so the archive version of that package is not what this row holds
JAVA_VERSION|no-autobump|openjdk-21-jdk-headless|the pin is the jdk major line inside an apt package name, so the point release the archive publishes is not what this row holds
RUST_CHANNEL|no-autobump|stable|rustup takes a channel and not a version, and resolving it to a number would freeze the channel this pin exists to follow
FLUTTER_CHANNEL|no-autobump|stable|the flutter download url takes a channel and not a version, and FLUTTER_VERSION is the row that moves
BENCHSTAT_REF|no-autobump|golang.org/x/perf|the module is untagged upstream, so `go install @latest` is the canonical install form and there is no release to compare against

# -------- no-autobump: the android toolchain --------
# THE INDEX EXISTS. https://dl.google.com/android/repository/repository2-3.xml
# is 408907 bytes of `<remotePackage>` entries and it carries all 3 of these:
# `commandlinetools-linux-<build>_latest.zip`, `platforms;android-N` and
# `build-tools;N.N.N`. Read on 2026-08-17 it held cmdline-tools 15859902 against
# the pin 14742923, platforms up to android-36 and build-tools up to 37.0.0.
#
# An earlier version of these 3 rows said no machine-readable index existed.
# That was false, and a false reason is worse than no rule: it reads as a
# decision somebody made. The true reason is that the android toolchain is 1
# decision and not 3 — the api level is chosen by what the app targets, the
# build-tools version is chosen with it, and a cmdline-tools build changes
# sdkmanager behaviour that google ships no changelog for — so these 3 move
# together, deliberately, or the weekly opens a pull request that silently
# retargets somebody's app.
ANDROID_CMDLINE_TOOLS_VERSION|no-autobump|dl.google.com/android/repository/repository2-3.xml|the index publishes the build number and this pin still is not resolved: a cmdline-tools build changes sdkmanager behaviour google ships no changelog for, and it moves with the 2 rows below it as one decision
ANDROID_PLATFORM_VERSION|no-autobump|dl.google.com/android/repository/repository2-3.xml|the pin is the android api level the app targets, so the newest platform the index lists is not the platform this image should install
ANDROID_BUILDTOOLS_VERSION|no-autobump|dl.google.com/android/repository/repository2-3.xml|the build-tools version is chosen with the api level above, so the newest one the index lists is not the one that goes with the platform this image installs

# -------- no-autobump: the tools WE release --------
# A release of ours is a decision, not upstream drift. cictl and hnslint are
# gophersys repositories that publish TAGS and no GitHub Releases at all —
# `releases/latest` is a 404 on both, forever — and the day they do publish one,
# the pin here still moves when we decide to consume it and not when the tag
# appears. Same class as the harness pins: 1 decision point, and it is ours.
CICTL_VERSION|no-autobump|gophersys/cictl|gophersys-owned and tag-only (zero github releases), and our own release is a decision rather than upstream drift, so this pin moves when we choose to consume a new cictl
HNSLINT_VERSION|no-autobump|gophersys/hnslint|gophersys-owned and tag-only (zero github releases), and our own release is a decision rather than upstream drift, so this pin moves when we choose to consume a new hnslint

# -------- no-autobump: the multi-product release stream --------
# bitwarden/clients publishes browser, desktop, web and cli under ONE release
# stream, and `releases/latest` is whichever of them shipped last: on 2026-08-17
# it was web-v2026.7.1, whose `cli-v2026.7.1` asset does not exist. Resolving
# this row bumped the pin to a version with no download — measured, 404, against
# the control `cli-v2026.3.0` which is 200. The fix is a tag-prefix filter in
# the coordinate grammar (`bitwarden/clients#cli-v`), which needs a release-LIST
# fixture this suite does not have; until that lands, an honest no-autobump.
BW_VERSION|no-autobump|bitwarden/clients|the release stream carries browser, desktop, web and cli together and github marks the newest of ALL of them latest, so resolving it bumps this pin to a version whose cli asset does not exist
