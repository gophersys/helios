# Underdetermination list — instance iE (run2)

Verbatim section (b) of the instance's return.

1. Runner errors have no home in the PIR schema. `conventions.multi-affirmation` says a partial presentation "is a runner error recorded in the PIR", but the PIR v0 skeleton and `pir_fields` define no such field. I added a top-level `runner_errors:` key. Schema extension required.
2. `q.env.conditions` — which values bound. The runner presented 6 of 8 (`drops`, `"none"` never offered) against "yes all the ones suggested". I bound only the 6 presented. Whether the 2 unpresented values become UNKNOWN, ABSENT, or simply unrecorded is undecided; I chose unrecorded + a runner error.
3. What a metric-less UNKNOWN blocks. `q.followup.range` feeds only PIR fields, no metric — yet R5 demands "listed with the P1 metrics it blocks". I named `metric.feasibility.env-risk` as an *indirect* block and said so; a strict reading would give `blocks: []`.
4. `pir.constraints[zephyr-rtos].strength` blocks a GATE, not a metric. Same gap in reverse: `blocks: []` is literally true but hides that G0 fails. I used `blocks: []` plus a note; there is no `blocks_gate` key in the spec.
5. THE decisive call — `pir.targets.unit_cost.sell` = UNKNOWN vs ABSENT. `conditional_fields` says an *explicit* not-for-sale → ABSENT, silence → UNKNOWN. The founder said "its just for me" (q.intent.who) and "2, and maybe 10 for my freinds", but never answered the sell half of `q.scale.cost` and never said "not for sale". I ruled UNKNOWN. This single call flips the whole verdict: ABSENT → economics scores amber → verdict go; UNKNOWN → core-unknown → verdict blocked. The contract does not say whether an answer to a *different* question can satisfy the "explicit" test.
6. Is `phone` a "tight pick" for `q.phys.size`? The graph says tight picks spawn `q.followup.range`; it never defines tight. The transcript shows no spawn, so I recorded `pir.physical.dims` = ABSENT (unspawned adaptive = N/A) rather than flagging a second runner error.
7. `q.power.duty` = "akwas on schel" is a typo with two plausible expansions ("always on…" vs "wakes on schedule"). I read `wakes-on-schedule` (it is the only matching enum value), which *is* what fires `derivations.capability.time`. Reading it as `always-on` instead would push `metric.feasibility.power-risk` toward red.
8. Which capability word `q.fn.offline` produces. It feeds `pir.functions` but the graph never names its S1 word. I chose `compute`. The coverage table only claims compute arrives via `q.fn.rate`.
9. `q.fn.rate` items: separate function items or attributes on the sensing items? I emitted them as separate `compute` items so the closed-vocabulary word `compute` actually appears in `pir.functions`, at the cost of duplicating the sense.
10. "not really" (q.novel.magic), "no rush" (q.time.proto). The `declared-none` convention enumerates only "no deadline / no threshold / not for sale". I extended it to these two. "no rush" → `none-declared` for proto is the weakest of the three readings.
11. `metric.risk.schedule` has no scale level for "no dates declared". Both feeds are answered (`none-declared`), so neither `unknown` nor `absent` applies, and it has no `absent_when`. I scored green on the reading that unbounded slack satisfies the green text — and said in the evidence that this means "no pressure exists", not "a schedule was validated".
12. `metric.viability.novelty` amber vs red. Commercial motorcycle GPS trackers arguably make "an existing product already is this" true. I scored amber because a difference *is* claimed. Also: `q.novel.moat` ("no compettiors") contradicts `q.intent.exists` ("yes, others exist") and no consistency rule covers this pair — a real gap in the graph's `consistency:` block.
13. `metric.risk.safety` — derived score vs a visible harm path. `scored_by: derived` = "no judgment", so `q.comp.safety = none` → green, even though "hopefully not explode" names a Li-cell hazard on a thermally hostile vehicle mount with `pir.environment.limits` UNKNOWN. The contract gives an agent no channel to downgrade a derived score; I recorded the tension as evidence only.
14. `metric.platform.compute-demand` — "as quick as possible" has no number. The derivation keys on *stated* rate periods (all ≥ 1 s → green), but an unquantified alert latency is exactly what would make it amber. Scored green, ambiguity named.
15. `agent+catalog` metrics against a 3-record catalog. The seam says "no coverage and no known example scores red". Cellular, GNSS, IMU and PMIC have zero catalog coverage but abundant shipped-product examples. The contract never says how the scorer establishes "known example" (no evidence base is specified for it), so both catalog metrics landed amber on my judgment, with 4 named research tasks. A scorer reading "no coverage" as sufficient for red would score `metric.feasibility.connectivity` red → verdict pivot.
16. `consumer` / `verdict_weight` / `human_gate_when` on score records. The scorecard skeleton shows only `id`/`score`/`evidence`/`blocked_by`. I carried `scored_by`, `verdict_weight`, `consumer` and `human_gate_when` through so the verdict rules are auditable from the scorecard alone.
17. `derived_evidence` and `human_gates_evidence`. F3 says "every score carries evidence lines", but the two derived flags and the human-gate determination are not `scores[]` entries and have no evidence slot. I added parallel keys.
18. PIR has no product/id field, yet the scorecard needs `pir: {ref, hash}`. I added `product: tracker` and a `source:` block, and used sha256 of the file bytes for `hash` (the hash algorithm and canonicalization are unspecified).
19. `pir.assets` when `q.time.exists = nothing`. `nothing` is a legal enum value; I recorded `assets: []` with the value preserved in provenance rather than `assets: [nothing]`.
20. G0 status has no representation anywhere. The PIR cannot state that it failed its own gate, and P1 has no rule for scoring a PIR that did not pass G0. I scored it anyway (as instructed) and recorded the G0 failure inside `recommendation.reasons` marked "recorded not blocking", since the contract defines `blockers` narrowly as open human gates + core unknowns.
