# Underdetermination list — instance iA (run1)

Verbatim section (b) of the instance's return.

1. Core-unknown vs G0 tier — a real contradiction. Rule 2 says a core `unknown` means "G0 should have prevented this". G0 cannot: `q.scale.cost` is tier `scoring` (UNKNOWN passes G0 by design) yet feeds `metric.viability.economics`, which is `core`. Any founder who skips the sell price forces `blocked` through a legitimately-passed gate. I scored it `unknown` → `blocked` and filed it as a defect report in `reasons`.
2. `sell` UNKNOWN vs ABSENT. "just for me", 2/10 units — no sale exists. ABSENT is only available where `conditional_fields` or `absent_when` declares it; neither does for `unit_cost.sell`. I chose UNKNOWN per R5. A one-line `conditional_fields` entry would flip the whole verdict.
3. `q.fn.talks` is a single-valued enum but the answer names two counterparts (phone-nearby *and* far-away-anywhere). I recorded two `connectivity` function items and treated `far-away-anywhere` as the binding enum value for derivation/consistency purposes.
4. `q.power.duty` likewise: enum, three values answered. `pir.modes` is a list so I kept all three — but `derivations.capability.time` tests `q.power.duty == wakes-on-schedule`, an equality that is undefined against a multi-valued answer. I fired it on membership.
5. "no rush" / "no deadline" for `type: date`. Not a date. I ruled these *answered* with value "none" (an explicit non-constraint), not UNKNOWN — which makes `metric.risk.schedule` green (unbounded slack). Reading them as UNKNOWN instead would put a minor metric in `blocked_by`.
6. `metric.feasibility.head-start` has no fitting level. Its red is a conjunction ("nothing — *and* the timeline assumes otherwise"); limb 2 is false here. Nothing exists, but nothing is assumed. I took amber as nearest defensible. Registry v0 scale gap.
7. `q.followup.range` unanswered blocks nothing. It feeds `pir.environment.limits`, which no registry metric consumes; `metric.feasibility.env-risk` is fed by the two answered questions. R5 demands "the metrics it blocks" — I wrote `blocks: []` plus a note, rather than inventing an indirect block on env-risk.
8. Unspawned adaptive → which sentinel? `q.followup.range` was never spawned for `q.phys.size`, so `pir.physical.dims` is neither UNKNOWN nor in `conditional_fields`. I used the literal `ABSENT`, borrowing the contract's word for branch-closed fields.
9. Volunteered-technology detection has no oracle. "any tech token in any answer" is undefined. I classified `gps` and `zephyr rtos` as volunteered tech left unclassified (→ G0 red); I deliberately did *not* count `cloud`, `pcb`, `antenna`, `led` as tokens. A different reading changes G0's status.
10. Unclassified constraints have no P1 home. `pir.constraints` feeds no metric, so a required-tier adaptive UNKNOWN cannot reach `blockers` (which holds only human gates and core unknowns). I put it in `reasons` as a second defect report and added `blocks_gate: G0` to the PIR unknown record — a key the spec does not define.
11. `derivations.capability.security|time|power` name no `pir_fields` entry — they have no home in PIR v0. I recorded them as `functions` items with `source: derived`, so S1's nine words close.
12. A negative answer to a required function question. `q.fn.acts` = "does not do anything to the bike". I recorded an `actuation` item with `present: false` (an undefined key) rather than dropping it, and excluded it from the `needs_hardware` count.
13. `metric.risk.safety` is `scored_by: derived` and mechanically green, but the verbatim is "no, just hopefully not explode lol" — a lithium cell on a vehicle rated for heat/cold/vibration/hosing. No registry lever lets a derived scorer escalate a founder's `none`, and `human_gate_when` fires on `serious` only. I scored green and escalated it in `reasons` for the G1 human.
14. `q.phys.size` maps to two values. "no bigger than a small phone ideally, deck of cards is ok" — I took the at-most bound `phone` (the question asks "at most").
15. `q.env.conditions` = "yes all the ones suggested" where the runner's proposal omitted `drops`. I recorded the six proposed, not all seven, and noted the omission.
16. The catalog seam vs. the metric scale disagree on `red`. The seam says "no coverage and no known example → red"; the metrics' own scales define red differently (no *known working example* / no radio reaches). GNSS, cellular and IMU have zero catalog coverage but obvious shipped examples. Per F2 ("the meaning of each level is written per metric") I let the registry scale win → amber, not red, on both `agent+catalog` metrics.
17. No per-answer timestamps exist in the transcript (only a file-level date). R4 mandates a timestamp per value. I recorded `at: '2026-08-26'` date-only everywhere rather than fabricate ISO seconds.
18. PIR top-level keys are prose-only (no lint tool exists yet: "PIR record type + provenance verification: PLANNED"). I added `product`, `source`, and `gate_g0`; and `provenance` is a list for every field, not only multi-fed ones.
19. `functions` provenance duplication. The spec puts item provenance inline, leaving no place for a feed that produced no item. I kept inline provenance and used the `provenance.pir.functions` entry only for the `q.fn.acts` negative.
20. Rule 4's "name every amber" doesn't say whether P2-class metrics count (they have no `verdict_weight`). Moot here since rule 2 stopped evaluation, but I listed `edge-autonomy`'s amber in `reasons` marked as non-verdict-bearing.
21. `derivations.pir.compliance.certifications` maps `us → [fcc]` only — an intentional cellular radiator also needs a carrier/PTCRB path. I did *not* add it to the PIR (derivations are mechanical) and named it as a research task inside the connectivity metric's evidence instead.
