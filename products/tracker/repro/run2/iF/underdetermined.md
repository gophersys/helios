# Underdetermination list — instance iF (run2)

Verbatim section (b) of the instance's return.

1. `pir.targets.unit_cost.sell`: UNKNOWN vs ABSENT — this single call decides the verdict. `conditional_fields` says an *explicit* not-for-sale is ABSENT and *silence* is UNKNOWN. The founder said "its just for me" and "2, and maybe 10 for my freinds" but never declared not-for-sale, and the runner never asked back. I chose UNKNOWN → core metric unknown → verdict `blocked`. Reading it as ABSENT instead makes economics amber and the verdict `go`. My tiebreaker: `declared-none` lists three example phrases, two of which ("no deadline", "no threshold") appear verbatim in the transcript and the third ("not for sale") deliberately does not.
2. Runner errors have no home. `conventions.multi-affirmation` mandates that a partial presentation be "a runner error recorded in the PIR", but no PIR field exists for it. I declared a top-level `runner_errors:` list (4 entries).
3. Which capability word `q.fn.offline` feeds. It feeds `pir.functions` but appears in no row of the coverage table. I used `compute` (edge autonomy = on-device logic); `connectivity` is defensible.
4. Function-item granularity from free-text `q.fn.senses`. "positon, altitude, speed, velocity, tilt, things like that" → I emitted 4 items (position, altitude, speed-velocity, tilt-motion), merged speed/velocity, and dropped "things like that". No rule governs splitting.
5. Where an adaptive `q.fn.rate` answer attaches. I nested a `rate:` sub-map with its own question/quote/at inside the function item (R4 per-item provenance). The spec never shows an adaptive-fed sub-field.
6. How to express ABSENT inside the PIR. `pir.physical.dims` — its adaptive never spawned. I wrote `dims: {}` with a comment; omission or an `ABSENT` sentinel were equally legal. The `absent` level exists only on the scorecard side.
7. `unknowns[]` shape. Spec is `{field, blocks}`. The zephyr-rtos unknown blocks no *metric* but hard-blocks *G0*, so I added a `note:` key rather than lose that fact.
8. `pir.constraints[]` shape. Spec is `{tech, strength, quote, at}`; `quote` is ambiguous between the strength answer and the sentence where the tech was volunteered. I recorded both (`quote` + `volunteered_in`/`volunteered_quote`).
9. No shape for `pair-number` / `pair-number-unit` values. I invented `{amount, currency, per_unit_at_qty, covers, bound}` for build cost and `{value, unit, qualifier}` for delight life.
10. `q.time.proto` = "no rush we are just testing out the system". Not literally "no deadline". I applied `declared-none`; UNKNOWN was the alternative and would have added a second minor blocker.
11. `metric.risk.schedule` with both dates none-declared. No scale clause covers "no dates at all". The registry declares no `absent_when` for it, so `absent` is illegal; I scored green (nothing can conflict) and said so explicitly in the evidence so it is not read as strength.
12. `metric.viability.novelty` amber vs red. "an existing product already is this" is arguably literally true of a motorcycle GPS tracker; the founder does state a difference, just an unverified one. I chose amber (minor weight — no verdict impact either way).
13. Admissible evidence for the red clause of `metric.tech.exists`. Red requires "no coverage AND no known working example". The catalog cannot prove a *known example*; the contract never says what off-catalog evidence qualifies or at what depth. I invoked the shipped-product class as cited agent judgment.
14. No rule for combining per-capability catalog levels into one metric score. This product is BLE-at-D1, GNSS/cellular/IMU-at-zero, barometric-at-D2. The seam gives per-capability levels only. I took the amber-with-named-gaps reading rather than red-because-one-capability-is-uncovered.
15. `metric.platform.compute-demand`: is an alert-latency wish a rate period? "within seconds, if an alert it must be as quick as possible". The derivation speaks only of rate periods (all ≥ 1 s → green). I scored green and flagged the latency wish in evidence so P2 does not inherit a false green.
16. The unpresented `drops` value on `q.env.conditions`. The convention voids binding for unpresented values but does not say whether they become UNKNOWN. I kept the field answered (six values), recorded a runner error, and created no UNKNOWN — otherwise `metric.feasibility.env-risk` would have had to go unknown despite two hard conditions already being affirmed.
17. `q.comp.safety` = "no, just hopefully not explode lol". No rule handles a verbal hedge attached to an enum answer. I recorded `none` → green (the scorer is `derived`, no judgment allowed) and preserved the aside verbatim in the evidence so the derived green does not launder it.
18. May P1 score a PIR that fails G0, and where does that appear? `recommendation.blockers` is defined as human gates plus core unknowns only, so the G0 failure fits nowhere structural. I scored P1 as instructed and carried the G0 block as an explicit `reasons` entry plus a header note.
19. PIR identity fields. The record spec has no `product`, `source`, or top-level `at`. I added all three (the slug `tracker` had to land somewhere).
20. `scores[]` extra keys. I added `scored_by` and `verdict_weight` (null on P2-class) for traceability; the record example shows neither.
21. `pir.hash` format. Unspecified — I used `sha256:` of the file bytes.
22. Transcription judgment on `q.power.duty`. "akwas on schel" read as "always on schedule" → `wakes-on-schedule`, and I did not select `always-on`. Selecting `always-on` instead would push `metric.feasibility.power-risk` toward red against a 1-month target.
