# Underdetermination list — instance iK (run4)

Verbatim section (b) of the instance's return.

1. `q.time.proto` = "no rush we are just testing out the system" — `declared-none-general` names "no deadline" and "no lowest threshold" as its examples. "No rush" is a statement of no time pressure, not literally a denial of a date. I read it as none-declared (which makes `metric.risk.schedule` green via its none-declared limb); reading it as UNKNOWN is defensible and would change that score to unknown/minor. Highest-risk call in the run — it is the same class of sentence that split run 3.
2. Function-item granularity — no splitting rule exists. `q.fn.senses` names "positon, altitude, speed, velocity, tilt, things like that". I emitted 5 sensing items (speed and velocity kept separate as named; the open-ended tail ignored). 1 item, 3 items, or 6 are all contract-consistent. Known named residual (12–16 items observed across instances).
3. `q.followup.range` spawn condition for `q.phys.size` — "tight picks open exact-dimension asks" never defines *tight*. I ruled `phone` not tight → `pir.physical.dims` = ABSENT (unspawned adaptive). If `phone` counts as tight, dims is UNKNOWN plus a fourth runner error.
4. `volunteered_quote` for `usb-c` — the token is volunteered at `q.power.source` and restated at `q.power.life`; the ask-back sits adjacent to the latter. The spec says "the sentence that volunteered the technology" without a first/nearest rule. I used the first volunteering.
5. `constraints[]` shape vs R4 — the record spec fixes the keys as `{tech, strength, quote, volunteered_quote, at}`, which carries no question id, yet R4 demands one per value. I put the question ids in `provenance.pir.constraints` as a parallel list; embedding them in the item is equally readable.
6. An unclassified volunteered token's `constraints[]` entry — the contract says the token is UNKNOWN and blocks G0, but never says whether a `constraints[]` item should exist for it. I emitted one with `strength: UNKNOWN`, `quote: UNKNOWN`; omitting the item entirely and carrying it only in `unknowns[]` is the alternative.
7. `constraints_excluded` is my invention — the oracle's exclusion list is normative but no field records that the exclusions were applied. Without it the gps/led/antenna judgments are invisible.
8. `metric.viability.outcome` green vs amber — the scale asks for "a measurable outcome". `q.intent.win` is checkable but carries no number. I read checkable-as-measurable.
9. `metric.tech.exists` scope — the registry's `fed_by` is only `q.novel.magic` ("not really"), while the contract's catalog seam scores across all functions. Named residual in the determinism doc. I scored across all functions; scoring the literal feed alone would give green.
10. The catalog-seam aggregation rule — no rule says how per-capability queries combine into one level. I took the worst-but-not-red (D2 barometer + D1 BLE + three uncovered-with-named-example capabilities → amber). Min, max, and majority are all unstated.
11. "within seconds" against the `compute-demand` `>= 1 s` threshold — the derivation compares numeric periods; "within seconds" has no number, and the same answer adds "as quick as possible". I treated it as >= 1 s → green, hedge carried in evidence. Reading the hedge as a sub-second requirement gives amber.
12. `metric.feasibility.power-risk` amber vs red — no quantitative rule bounds "violates the power class physically". 1 month on a rechargeable pack with duty-cycled GNSS+cellular is aggressive; whether it is *impossible* is a BOM judgment the contract does not supply.
13. `g0.checks[].result` for "graph lints clean" — G0 condition 4 is a check on the graph artifact, not on this record, and no tool ran. I recorded `not-evaluated` rather than asserting a pass; the contract offers no way to record a check outside the extractor's reach.
14. `decision` empty representation — `{}` vs the key omitted vs `null`. I used `{}`.
15. Timestamp precision — the transcript carries only the date 2026-08-26, so every `at` is date-only, which the `timestamps` convention permits but the PIR example (`2026-08-26T17:40:00Z`) does not model.
16. `environment.notes` / `physical.notes` / `functions_notes` are my additions — `carry-placement` says "the concealment detail goes to notes" without declaring a notes field anywhere in `pir_fields`; strictly, no such field exists to write to.
