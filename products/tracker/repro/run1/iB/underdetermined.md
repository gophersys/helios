# Underdetermination list — instance iB (run1)

Verbatim section (b) of the instance's return.

1. No timestamps. R4 demands question+quote+timestamp; the transcript carries only a file-level date. I used date-only 2026-08-26 everywhere rather than invent a clock time.
2. `q.fn.talks` is a single `enum` but the answer names two values (far-away-anywhere AND phone-nearby). No multi-answer rule exists. I recorded both as function items and treated `far-away-anywhere` as the binding value for `metric.feasibility.connectivity`.
3. `q.power.duty` same problem, three values named. `pir.modes` is a list, so I recorded all three; `derivations.capability.time` fired on membership of `wakes-on-schedule`, which the graph words as equality.
4. `q.scale.cost` is a `pair-number` answered on the build half only. No rule covers a half-answered pair. R5 → `sell: UNKNOWN`. This single call decides the verdict: it makes a core metric unknown → `blocked`. The alternative ("personal build, never sold → absent") is closed off because `absent` needs an `absent_when` and `metric.viability.economics` has none.
5. Contract gap exposed by #4: `metric.viability.economics` is `core` but both feeds are tier `scoring`, so G0 legitimately passes the UNKNOWN and P1 then blocks on it. Rule 2's parenthetical ("G0 should have prevented this") is false in this configuration. `metric.tech.exists` has the same shape (core, fed only by scoring-tier `q.novel.magic`).
6. Declared absences vs UNKNOWN, twice. `q.power.life` floor = "no lowest threshold"; `q.time.proto`/`q.time.prod` = "no rush"/"no deadline". Types `pair-number-unit` and `date` have no representation for an answered-none. I invented `{declared: none, raw: …}` and `{date: none, statement: …}`, and scored `risk.schedule` green (not unknown).
7. Volunteered-technology detection is undefined ("any tech token in any answer"). The runner asked back on `cellular` and `usb-c` only. I flagged `gps` (q.intent.what) and `zephyr rtos` (q.novel.magic) as unclassified → G0 red. I deliberately did NOT flag `cloud`, `led`, `button`, `pcb`, `antenna`. A different instance will draw this line elsewhere.
8. The `unknowns` record `{field, blocks}` cannot express a gate-blocking UNKNOWN. `q.constraint.strength` feeds no metric, so `blocks: []` — yet its tier is required and it hard-blocks G0. I added a `gate_status:` block (extension) to say so.
9. `field:` must name a PIR field, but a per-item constraint strength has no address. I invented `pir.constraints[gps].strength`.
10. Derived capability words have no home. `derivations` writes `capability.security/time/power`, which is not in `pir_fields`, and PIR v0 has no `capabilities:` field. I put them in `pir.functions` with `derived: true` + the rule cited.
11. `compute` likewise. The coverage table says it arrives via `q.fn.rate`. I attached rates inline to the sensing items *and* synthesized one `compute` item so the S1 word is not silently unfed.
12. A negative answer to a required function question (`q.fn.acts` = "it does not do anything to the bike"). Nothing says whether that yields an `actuation` item with detail "none" or no item. I produced no item and kept the answer in field-level provenance.
13. `pir.physical.dims`. The `q.followup.range` spawn for `q.phys.size` never fired although `deck-of-cards` is a tight pick. "Unspawned adaptive is N/A" → I omitted the key (ABSENT). `conditional_fields` only covers `battery_life`, so this absence is by inference.
14. `q.phys.size` names both a ceiling and an acceptance ("no bigger than a small phone ideally, deck of cards is ok"). The ask is the maximum → `phone`.
15. `q.env.conditions` = "yes all the ones suggested" is resolvable only via the runner NOTE, not the answer. `drops` was not in the proposed six, so it is not selected — the answer alone could mean all seven.
16. `metric.feasibility.head-start` fits no level. Red is conjunctive ("nothing — AND the timeline assumes otherwise") and the second conjunct is false; amber's text ("rough sketches or a 3D model only") is also false since nothing exists. I honored the written conjunction → amber. Red is equally defensible.
17. `metric.viability.novelty`: red and amber both match literally ("an existing product already is this" vs "difference is incremental or unverified"). Chose amber. Minor weight, so no verdict effect.

Does not move the verdict here, but under a different economics answer it decides pivot-vs-go.
19. `metric.feasibility.connectivity` green text conflicts with the seam. Green says "covered by the supported-SoC lanes (catalog D1+)"; the seam says D1 scores amber. All catalog SoC coverage is D1. I followed the seam → amber.
20. No aggregation rule for multi-capability metrics. Both `agent+catalog` metrics score a product that needs several capabilities at different depths (D2 BME280, D1 esp32c6, no record for three others). I took worst-case.
21. Whether `reasons` is populated on a `blocked` verdict. Rule 4 defines reasons only on the go path, and evaluation "stops" at rule 2. I populated it anyway, keeping `blockers` distinct.
