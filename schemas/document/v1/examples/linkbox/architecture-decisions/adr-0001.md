## Context

REQ-0001 requires that saving a link be durable and confirmed, and REQ-0004 sets a 300ms p95
budget on the save and library calls. The backend (CMP-0001, `linkbox-api`) and the web client
(CMP-0002, `linkbox-web`) are built by separate work packages that must proceed in parallel
against a stable boundary, and the web client is generated, type-safe, and browser-resident.
The question is what shape the client-server boundary takes: a hand-written REST/JSON surface,
GraphQL, or a schema-first RPC. A hand-written REST surface drifts from its clients and leaves
parallel teams negotiating field names in review; GraphQL adds a query layer the product does
not need (the access patterns are a small fixed set).

## Decision

We will define the client-server boundary as Connect RPC services with protobuf as the source
of truth, beginning with the frozen `LinkService` (CTR-0001). The `.proto` is the contract:
the Go server and the Svelte client both generate from it, so the boundary cannot drift and the
two work packages can be built concurrently against a checked shape. We reject hand-written REST
(no single source of truth, drift-prone) and GraphQL (query flexibility we do not need, at the
cost of a heavier server and N+1 risk against the latency budget).

## Consequences

Easier: the contract becomes a generated, type-safe artifact both cells share, so parallel
builds of CMP-0001 and CMP-0002 are safe and the freeze in service-contracts is mechanically
enforceable. Connect's binary-over-HTTP keeps the save path lean, which helps the REQ-0004
latency budget. Harder: every boundary change now flows through a `.proto` edit and codegen
step rather than an ad-hoc handler tweak, and contributors must learn the Connect toolchain.
We take on a build-time codegen dependency and commit to keeping generated clients in sync,
which is the price of the no-drift guarantee.
